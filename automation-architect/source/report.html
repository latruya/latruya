Recommendations report

Automating controls engineering with Claude and vendor AI

A recommended architecture for taking a project from specification to tested, simulated and documented control software, across the major automation platforms and under each industry's rules.

The architect

Claude Code, packaged with the Claude Agent SDK, plans the project, directs the work and checks the result.

The specialists

Each vendor's own AI and engineering tools build inside their platform: Siemens Eigen, Rockwell FactoryTalk Conductor, Beckhoff CoAgent and others.

The proof

Every requirement is tested against a simulated plant. The results become the evidence in the documentation set.

15 November 2026Vendor information as published to this date

01The recommendation in brief

Make Claude Code the architect. Run it on Claude's most capable model, package it with the Claude Agent SDK so the same pipeline runs on every project, and connect it to each vendor's own AI and engineering tools. You supply the specifications. The architect drafts the design, directs the vendor tools to build the software, proves it against a simulated plant, and assembles the documentation your industry requires. People approve the work at defined gates.

  1. Claude Code with the Agent SDK is the architect. Vendor engineering tools such as TIA Portal, Studio 5000 and DeltaV are licensed Windows applications on your own network. The orchestrator has to run beside them, with access to project files, scripts and version control. Claude Code and the Agent SDK are the Claude products built to run on your machines with that access.
  2. Vendor AI does the platform-specific work. Siemens, Rockwell, Schneider Electric, Beckhoff and CODESYS all shipped or announced AI for engineering in 2026: agents in some cases, open agent interfaces in others. These tools know their own platforms better than a general model does. Claude specifies the work, hands it to them, and checks what comes back.
  3. Simulation is how the architect tests itself. A separate test agent writes a test for every requirement. Tests run on emulated controllers against a plant model, failures go back to the build step automatically, and passing runs are stored as evidence.
  4. Industry rules are packaged as Skills. One pack per industry defines the lifecycle, the deliverables and the templates: GMP for life sciences, functional safety for process plants, machinery safety for discrete manufacturing. Changing industry means loading a different pack.
  5. People stay accountable. Approval of requirements, design, safety functions and release stays with named people. In GMP work this is a regulatory requirement.

What is realistic today

"Specifications in, finished product out" is achievable as a gated pipeline. It is not achievable as an unattended one. Two things set the limit. Regulated industries require human review and signature, and the vendor agents are new and partly closed. Siemens, for example, documents no way for an outside agent to call Eigen, so that hand-off currently goes through an engineer or through TIA Portal's scripting interface.

The drafting, generating, testing and documenting can be largely automated now. The deciding and approving cannot, and should not be.

What you provide

  • User requirements or a process description
  • P&IDs and an I/O list or instrument index
  • Control narratives or sequence descriptions
  • Site standards, naming rules and module libraries
  • A platform preference, or leave the choice to stage 2
  • The industry, which selects the pack

What comes out

  • The control project in the vendor's own format
  • A simulation model and an automated test suite
  • An evidence pack tied to requirement numbers
  • The documentation set for the chosen industry
  • A full Git history of every change and approval

02The architecture

The system has four layers. People sit at the top and supply specifications and approvals. The architect and its specialist agents sit in the middle. Vendor AI, engineering tools and simulators sit at the bottom, reached through one connection standard.

How the layers divide the work

The architect holds the whole project in view. It reads the specifications, decides the order of work, delegates to specialists, and refuses to move past a gate until the required person has approved. It never edits a live controller.

Subagents are separate Claude instances with their own instructions and their own context. The separation matters most for testing: the agent that writes tests works from the approved requirements and never sees the code, so it cannot repeat the builder's mistakes.

MCP, the Model Context Protocol, is the open standard for giving an AI agent tools. Beckhoff and CODESYS already publish MCP interfaces. For vendors that do not, a small MCP server wrapped around the vendor's documented scripting interface does the same job.

Git holds every artifact: requirements, design documents, exported project files, tests and results. Anything the architect produces can be compared, reviewed and rolled back.

Keep the design independent of the vendor

Have the architect hold the design in a neutral form before any vendor tool is touched: equipment and control modules, interlocks, sequences, alarms and I/O as structured data. Vendor-specific generation is then the last step. This lets one design serve several platforms, protects you while the vendor agents mature, and gives the test author something to work from that is not the code.

07Simulation: how the architect tests its own work

Self-simulation is what makes the rest trustworthy. The architect does not judge its own code by reading it. It loads the code into an emulated controller, runs the plant model against it, and compares the behaviour with what the requirements say should happen.

BuildGenerate or change the code
LoadDownload to an emulated controller
RunPlay scenarios against the plant model
CompareCheck behaviour against each requirement
EvidenceStore results by requirement number
any failure: diagnose, fix, run again

2 Virtual acceptance test hours per runThe same emulated controller against the vendor's high-fidelity digital twin of the process or machine.SIMIT, NX Mechatronics Concept Designer, Emulate3D, Mimic, UniSim Design, AVEVA Dynamic Simulation.Proves timing, dynamics and operator screens before factory acceptance. Also trains operators.

Rules that keep the testing honest

  • Independent tests. The test author works from approved requirements and never sees the code.
  • People review the test cases, not only the results. A wrong test that passes proves nothing.
  • Inject faults. Break the code on purpose and confirm the tests fail. Tests that cannot fail are removed.
  • Record the conditions. Each run stores the software version, test version, simulator settings, time and result per requirement.

What simulation does not replace

  • Checks of field wiring and I/O at site
  • Instrument calibration and real device behaviour
  • Network timing and hardware faults on the real system
  • Mechanical and process reality that the model simplifies

Site acceptance testing stays. Simulation moves most defects from site to the desk, where they are cheap to fix.

Regulation to watch: draft EU GMP Annex 22

The European Commission consulted on a new Annex 22 on artificial intelligence between July and October 2025, together with a revised Annex 11. As of November 2026 neither has been adopted. The draft says generative AI and large language models should not be used in critical GMP applications, and permits them in non-critical uses where a qualified person reviews the output. The European Medicines Agency held a workshop on generative AI in mid-2026, so the final text may differ.

The draft addresses AI built into manufacturing systems. An engineering assistant whose every output is reviewed by people and verified by conventional testing is a different use. That reading is this report's interpretation, not a regulatory ruling. Have your quality unit confirm it and check again when the final text appears.

09Guardrails: what the architect must not do alone

Each risk below has a control that the system enforces. None is left to the model's judgment.

RiskControl
Logic that looks right and is wrongLibrary modules first. Independent tests written from requirements. Simulation evidence for every requirement. Human design review at the gate.
Safety functionsThe architect drafts and checks only. Safety instrumented systems and safety PLC logic are designed and verified by competent people, with the independence that IEC 61511 and ISO 13849 require, and kept separate from basic control.
Changes to a live plantNo network path from the architect to production controllers. Hooks block production address ranges. Authorized people download to real controllers under change control.
Confidential designs leaving the companyUse Claude under commercial terms, where Anthropic does not train on your data by default. Run the architect on your own machines. Check each vendor's cloud AI terms as well, since Eigen is a cloud service.
Work that cannot be traced or repeatedGit as the single source of truth. A log per deliverable of instructions given, tools called, and model and skill versions used. Versions are fixed per project and changed only after re-running a reference project.
The same AI writing code and testsSeparate agents with separate context. Human review of test cases. Fault injection to prove the tests can fail.
Vendor agents that are new and unprovenKeep the design in neutral form. Treat vendor productivity figures as unverified until your pilot measures them. Confirm licence terms for scripted use of engineering tools.

10How to start

Start with one platform and one finished project to use as a reference. Build in order of lowest risk: documents, then code, then closed-loop simulation. The timings are indicative.

Weeks 1 to 4
Foundations

Choose the pilot platform and a reference project. Put standards, templates and libraries in Git. Install Claude Code beside the vendor tools. Write the first skills.

Months 2 to 3
Specifications and documents

Automate stages 1, 3 and 6. Compare the output with the reference project's real documents.

Months 3 to 6
Build and unit test

Connect the vendor AI and scripting interfaces. Build the module library. Run unit tests on an emulated controller.

Months 6 to 9
Closed-loop simulation

Add plant models and the virtual acceptance test. Package the pipeline with the Agent SDK. Add hooks and the audit log.

Months 9 to 12
Live pilot

Run a real project alongside conventional delivery. Have quality review the approach. Then add a second platform or industry.

Which platform to pilot

Choose the platform where you have the most projects and the best module library. Given your interest in Eigen and in life sciences, a Siemens TIA Portal skid or process unit is the natural first pilot. Eigen is shipping and was piloted with over 100 customers, and PLCSIM Advanced with SIMIT gives a scriptable simulation chain. If a direct connection to Claude matters more than installed base, start with Beckhoff or CODESYS.

Questions to settle with vendors

  • Siemens: does Eigen offer any outside interface, which tasks does it cover, and what are its licensing and data terms?
  • Rockwell: can Conductor use Claude as its model, and can an outside agent start its workflows?
  • Emerson and Honeywell: what is planned for configuration generation?
  • All: do licence terms allow scripted and unattended use of the engineering tools?

AppendixTerms, method and sources

Terms used

Agent. An AI model that carries out multi-step work with tools, rather than answering one question.
MCP. Model Context Protocol. An open standard for connecting an AI agent to tools and data.
Skill. A versioned folder of instructions, templates and scripts that Claude loads when a task calls for it.
Subagent. A separate Claude instance with its own role and context, directed by the architect.
Hook. A script that runs automatically before or after an agent action and can block it.
Emulated controller. Software that runs the real controller program on a PC without the hardware.
GAMP 5. The ISPE guide to risk-based validation of computerised systems in regulated life sciences.
Traceability matrix. A table linking each requirement to its design element, test and result.
Openness, Logix Designer SDK, FHX. The scripting or file interfaces of TIA Portal, Studio 5000 and DeltaV.
Virtual acceptance test. A factory acceptance test run against a simulated plant before hardware exists.
